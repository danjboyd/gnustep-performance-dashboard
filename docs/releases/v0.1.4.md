# Performance Dashboard v0.1.4

**Local release-notes draft; not published.** Planned scope is Linux,
Debian 13 amd64. Numeric-final source, asset hashes and final-package
acceptance are pending. The completed RC1 is documented separately in
[its ledger](v0.1.4-rc1.md). This draft does not authorize a release.

## Changes since v0.1.3

- **Record native targets launched through exec wrappers.** A dynamically
  linked shell wrapper that execs the target in the same process can retain
  recording injection. The reader recognizes a replacement stream epoch and
  displays the final native executable's samples and identity. Events before
  the final exec are discarded; this does not preserve a multi-image history.
  Child processes remain excluded unless explicitly followed.
- **Keep the viewer responsive while opening existing traces.** Parsing,
  record resolution, analysis preparation and initial CPU-tree construction
  run on a worker while standard progress UI is visible. AppKit publication
  and drawing stay on the main thread. Closing the window discards the
  eventual result; it does not yet cancel parsing.
- **Reduce memory used by finished allocation-rich recordings.** Stable
  index sorting avoids a large event-sort scratch copy, storage is trimmed
  and analysis capacity follows allocation count. Compact finished records
  refer to event storage; requests for the public contiguous records array
  materialize it on demand and can increase memory again. Live streams keep
  their separate expanded representation.
- **Refresh Linux packaging inputs.** CLI v0.1.3 and packager v0.1.6 replace
  the v0.1.3 app's CLI v0.1.2/packager v0.1.4 pins. Dependency versions are
  distinct from the app version. The checked runtime archive and updater
  implementation bytes remain unchanged; this is not a new runtime fix.

On one retained 340,831,476-byte allocation-rich input, earlier local
three-run measurements observed about 17% less peak RSS and 16% less loaded
RSS than the earlier responsive-loader build. Final RC1 acceptance observed
no main-loop hangs of at least 250 ms on one open. These are profiled,
workload-specific observations, not general latency, throughput or memory
guarantees. See [validation](../v0.1.4-validation.md) for exact inputs,
versions, measurement boundaries and the public-array materialization cost.

## Download, recording and updates

Planned assets are `PerformanceDashboard-0.1.4-x86_64.AppImage`, its `.zsync`,
provenance JSON, stable update-feed JSON, corresponding-source archive and
`SHA256SUMS`. Exact identities are pending the numeric-final build and audit.
The [final checklist](../v0.1.4-plan.md#numeric-v014-final-checklist) requires
the published v0.1.3 stable app to upgrade to the exact numeric v0.1.4 bytes,
including replacement/relaunch and refusal/retry checks. RC1-as-stable
installation fixtures do not satisfy that route. No v0.1.4 public feed has
been deployed.

Use X11 or XWayland on Debian 13 amd64. Existing
[v0.1.3 host prerequisites](v0.1.3.md#download-and-run), including host
libunwind for optimized stacks and binutils for source lines, remain relevant.
Targets use their own runtime; the viewer supplies its packaged GNUstep
environment. The optional privileged helper is only needed for attachment.

## Limits and pending acceptance

The trace format remains v1. Updates rely on HTTPS and SHA-256 without an
independent package/feed signing trust root. Dynamic-loader restrictions
still apply to injection. Conservative leak candidates are not proof of
leak freedom. Closing a large load does not stop its worker, and requesting
expanded public allocation records can raise memory use. Native Windows
packages and acceptance remain deferred. The experimental Markdown Viewer
GNUstep attribute-cache change is not included in this release.

Numeric-final source/tag target: **pending**. Final acceptance receipt and
six asset hashes: **pending**. RC1 source is
`ac24ff4b83db2956a9d7e7761ff9c763696eb393`; it passed the exact-source
73-check gate including 28 unit tests and the separately recorded Linux
package/helper/both-theme GUI/updater/wrapper/large-trace acceptance. Those
results remain RC1 evidence. Final-byte reruns and the real stable-version
upgrade route must pass before this section can describe final acceptance.
