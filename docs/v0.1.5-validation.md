not a synthetic trace or a change to shipped code or the installed SDK.

## Signed-chain observations

`Tests/update-chain-checks.py` compiles an ARC test adapter against the built
GPUpdaterCore, which reads/selects a local feed before passing its selected
fields to the built helper. Fresh throwaway keys and disposable shell payloads
are used. The helper SHA-256 was
`3c608e71b7ef5d5df186bd692c23576868b7e09a7728c99eb5a39af0b1ea7235`.
No network service, real AppImage, real installation or GUI relaunch was used.

| Case from a 0.1.5 fixture | Observed behavior |
|---|---|
| Correct signed test 0.1.6 bytes | Prepared and applied; installed bytes matched exactly |
| Changed asset with original feed hash | Refused; installed copy unchanged; hash-mismatch download retained |
| Changed feed signature | Refused; installed copy unchanged; rejected download removed |
| Changed asset and recomputed feed hash/size, original signature | Refused; installed copy unchanged; rejected download removed |
| Missing feed signature | Refused; installed copy unchanged; rejected download removed |
| Feed version/tag changed to 0.1.6.1, signed bytes untouched | Selected and ready to apply; deliberately not applied |
| Feed advertises 0.1.6, genuine signature of older 0.1.4-test bytes | **Accepted and installed the older fixture bytes** |
| No-key client with failing test `appimageupdatetool`, no zsync feed field | Selected alternate tool; failure left installed copy unchanged, with no direct-download fallback |

These eight scenarios matched the recorded current behavior. They are not
eight claims of secure refusal. Signatures cover asset bytes, not feed
metadata or release identity; the older-payload case shows no payload-version
comparison in this path. **Anti-rollback is not provided by these checks.**
No behavior fix was made. The metadata/rollback findings were sent to the lead
for scope/release review; the lead assigned any fix to the packager's helper.
The observational assertions deliberately fail if a later helper refuses the
currently accepted metadata/rollback cases, so that its new boundary is reviewed.
The [retained chain receipt](qualification/v0.1.5-update-chain.json) records
exact binary/test identities and outcomes without key material or host paths.
The legacy helper source is byte-identical between
the released v0.1.4 commit and this tree; this fixture observation does not
replace acceptance with an actual old AppImage.

The first adapter build encountered the vendored API's ARC-reserved `release`
getter; the test adapter uses KVC at that boundary. A first runtime assertion
incorrectly assumed every rejected download was deleted; the harness now
records the distinct hash/signature cleanup behavior. Early logs are retained.
