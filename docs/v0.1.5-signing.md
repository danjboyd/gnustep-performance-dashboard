# Local v0.1.5 update-signing preparation

This is local plumbing and a test plan. No product key/secret was read or
created, no release asset was built, and nothing was pushed or published.
Only freshly generated throwaway keys and synthetic local payloads were used.
Release scope, version bump, arm64 inclusion and publication remain separate
Dan decisions.

## Inputs and order

`updates.publicEDKey` is explicitly null in the source manifest until Dan
provides the product trust anchor. The packager accepts that preparation
state; **release packaging requires** a valid 32-byte base64 public key in
`UPDATE_ED_PUBLIC_KEY`. A generated sibling manifest embeds it before staging,
without altering the tracked manifest. The extracted package must contain
that same key; provenance records it for the release-assembly check.

The Linux release job names the repository variable `UPDATE_ED_PUBLIC_KEY`.
The later assembly job names the secret `UPDATE_ED_PRIVATE_KEY` and the same
public variable. These are references, not created settings. The private input
is base64 of a 32-byte Ed25519 seed or a 64-byte seed+public pair; its derived
public key must match the expected public key. Key material is kept in a
mode-0600 temporary file removed on exit and is never printed.

The workflow signs AppImage payload **bytes**, then verifies the signatures,
then assembles the distribution feed/site copy and final SHA256SUMS. The
packager's unsigned feed is intermediate build metadata. Assembly with
`--require-signatures` independently checks the payload signature and the
packaged/provenance public key before writing any releasable output. The
existing non-required mode remains available for historical artifact review.
This does not sign the JSON document itself or claim that release-note text
is authenticated. A signing failure leaves the feed unchanged.

The implementation is adapted from ObjcMarkdown's
`packaging/ci/sign-update-feed.py`. No unrelated project code or upstream
submission is involved.

## Local checks run

- `Tests/update-signing-checks.py`: seven checks passed with both the actual
  vendored updater helper and pinned packager available, no skips. Fresh
  throwaway keys covered valid/bad/missing signatures, wrong public/private
  pairing, 32/64-byte private-input forms, changed payloads, missing inputs,
  atomic failure, manifest generation, and public-key propagation into the
  packager's runtime config.
- The real updater's independent Monocypher verifier refused bad and missing
  signatures, left the installed fixture untouched, and removed rejected
  downloads. A valid local `file://` fixture moved from the synthetic 0.1.4
  installed bytes to 0.1.5 bytes through actual prepare/apply states. No
  dry-run bypass or network service was used.
- `Tests/release-assembly-checks.py`: fourteen checks passed, including signed
  final-feed/checksum preservation and refusal of missing/bad signatures or
  a mismatched packaged public key. All artifacts were synthetic and temporary.
- The pinned v0.1.7 packager's manifest check passed. Shell syntax and release
  workflow structure checks passed. The workflow signs before final feed
  assembly and names the private-key secret only in that signing step.

No real AppImage packaging run, hosted CI run or public feed verification is
claimed. A first Python-only run skipped the helper case; the later complete
integration run above exercised it. A cleared temporary SDK link was restored
to the retained owned SDK; no installed runtime was changed.

## v0.1.4 to v0.1.5 update-path plan

The runnable local-helper fixture is a trust-configured client test, not a
claim that the existing released v0.1.4 client already contains the future
public key. A legacy client without `publicEDKey` uses its existing SHA-256
path and may use AppImageUpdate; receiving a signed feed does not retroactively
make that client's first update authenticated by this new key.

Before claiming a complete product update path:

1. Dan supplies the product public key and provisions the matching private
   secret separately. Decide the first-trust-anchor distribution path; do not
   describe the legacy hop as signature-enforced.
2. Build an explicitly approved candidate. Inspect its runtime updater config
   and provenance for the public key, and verify signatures before assembly.
3. On disposable copies, serve local release bytes/feed and run the existing
   private-home/private-Xvfb update harness from a v0.1.4 copy to the candidate.
   Check replacement and relaunch; record the legacy trust limitation.
4. With a key-configured client copy, reject bad/missing signatures and changed
   bytes without replacing the installed copy, then retry the correct local
   update and confirm replacement/relaunch. Exercise both Adwaita and Sombre
   if the application UI changes or its acceptance gate requires them.
5. Keep public feeds, actual installations and real keys untouched until the
   corresponding exact in-session authorization is given.

Steps involving actual candidate packaging, a real key or GUI relaunch have
not run in this local plumbing interval. The throwaway local-file helper
prepare/apply portion has run as described above.
