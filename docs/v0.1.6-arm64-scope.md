## Concrete packaging dependencies

| Layer | Current inspected constraint | Needed before an aarch64 package |
|---|---|---|
| Packager tool/payload architecture | AppImage defaults name x86_64 artifacts and an x86_64 appimagetool; backend invocation sets `ARCH=x86_64`; extracted runtime is named `runtime-x86_64` | Explicit host-tool and target-runtime architecture, matching pinned tool/runtime checksums, correct output naming; renaming an x86 binary is insufficient |
| Toolchain and shell | Project locks contain Linux amd64 GNUstep payloads and x64 PowerShell | Reviewed, signed/pinned native arm64 toolchain including AppKit, back, theme and test tools, plus compatible PowerShell input; no ARM release asset availability was verified here |
| Runtime closure | `scripts/stage-linux-runtime.py:host_linker_cache` accepts only `x86-64` ldconfig rows | Architecture-aware dependency discovery, ELF-machine validation, stripping/RUNPATH and notices checks on actual arm64 staged binaries |
| Project package scripts | `package-linux.sh` hardcodes x86_64 AppImage/provenance names; existing clean builder/input locks target Debian 13 amd64 | Explicit architecture input throughout build, stage, provenance, source inventory and collection, preserving current x86 behavior |
| Release assembly | One asset per backend/feed; AppImage platform must equal `linux-x64` | Architecture as part of identity/validation and feed policy, with wrong/mixed-architecture refusal checks |
| Helper acceptance | `check-helper-vm.sh` launches `qemu-system-x86_64` with x86 guest/kernel assumptions | Separate ARM kernel/VM recipe and native permission/attach acceptance; keep the privileged helper small and defensive |

The agent must continue to depend only on libc. Inspect the built ARM agent's
ELF dependencies and dynamically resolved Objective-C/unwind behavior; do not
link GNUstep, libobjc or a C++ runtime into it as a packaging workaround.
Do not replace a trial application's installed runtime or add optional symbol
packages without that application's separate approved plan.

## Feed and client compatibility is a prerequisite

The current packager's `scripts/lib/core.ps1:Get-GpUpdatePlatform` returns
`linux-x64` for every AppImage. The vendored GPUpdaterCore parses/stores an
asset's platform, but `Source/GPUpdater.m:_preferredAssetForRelease` selects
the **first asset matching only the backend**. It does not compare platform
or architecture. These are source findings, not a mixed-feed execution test.

Consequently, adding an aarch64 asset to the current shared Linux release
entry is not a safe migration by itself. Existing v0.1.5 clients retain their
selection behavior even if a future client becomes architecture-aware. A
valid payload signature also does not by itself establish that the payload
matches the client's architecture or advertised release identity.

The lead selected one future Linux feed containing x86_64 first and aarch64
second, using the new architecture-aware client expected in packager v0.1.9.
Canonical platform tokens are `linux-x64` and `linux-arm64`; absent platform
means legacy x64 only. The ordering is required because installed v0.1.5
clients retain first-backend-match selection. This is a planning decision;
no new updater, signature code, combined feed or ARM package is adopted here.

A separate ARM feed remains the fallback if that compatibility contract cannot
be verified: preserve the existing Linux stable feed for legacy x64 and
explicitly configure ARM clients to a different path. No fallback feed is
approved or deployed here.

Whichever strategy is selected, qualification should include both client
architectures, wrong-architecture assets, missing/malformed platform fields,
stable/prerelease separation and signed-payload identity checks. Preserve the
existing metadata/rollback limits until the helper's actual contract changes.
Keep x86 feed contents and publication permissions separate from ARM work.

## Build and qualification options

| Option | Appropriate use and unresolved work |
|---|---|
| Isolated native ARM builder | Preferred release-build path: matching dependencies and direct execution. Needs a pinned full GUI toolchain, adequate scratch space and a separately approved machine/runner plan |
| Hosted native ARM runner | Possible CI producer if the project's actual runner availability, capacity and permissions are confirmed; none were checked or scheduled here |
| Existing local QEMU VM | Development/regression coverage. Its retained private SDK is headless; a full AppKit/back/theme build and private-display gates are additional work. Emulation does not replace real hardware timing or recorder qualification |
| Cross build on x86_64 | Requires a pinned sysroot, separate host tools versus target payloads, correct runtime closure and later native execution. Current scripts do not establish this path; it is a larger first-release route |

Before selecting an ARM release candidate, require a clean source/integration
identity; full strict units/CLI/private-home and both-theme GUI gates; package
extraction, ELF/RUNPATH/dependency and corresponding-source checks; disposable
helper checks; real hardware recording/save/reopen; sustained/multithreaded,
CPU/unwind and Leaks cases; and a local signed update/relaunch/refusal run.
Record JPEG conditional-probe disposition and live fixture checks separately.
No prior x86 AppImage result or single short ARM allocation smoke substitutes
for those gates. Measure actual GUI build/package storage before proposing a
trial on a disk-constrained machine.

The next planning decisions are the exact upstream packager/toolchain inputs,
feed migration and platform identifiers, native builder/CI ownership, hardware
qualification plan and ARM release order. No deployment, purchase, upstream
post or host action is implied by this scope note.
