# v0.1.4 real-application profiling

Local, prepared-only evidence from October 29, 2026. Every target was built
and run in an owned clone, with a private passwd home, temporary directory
and newly allocated Xvfb display. No user's desktop, owner checkout, real
directory scan or upstream submission was used. These are diagnostic
workloads, not independent release acceptance for the target applications.

## Markdown Viewer: layout dominates the large-document workflow

Unchanged source: `8178c1e5009a2673d14feb5ae7049cb0ccc31434`.
Native executable SHA-256:
`745433d92c6cfdce567febfbd2d8e4321009f8fedac415d028b004a1bb139757`.
The 400-section generated local document is 460,726 bytes, SHA-256
`38846406c525580b327ac17d2e052ba7bdb7813e76341155406ba4ecaaf937e2`.
It has headings, styled paragraphs, internal links, tables and code blocks,
with no remote images, math, Mermaid, network or database workload.

Adwaita completed Read/open, scroll, Edit, a verified saved marker, Split
and preview scrolling. The saved file SHA-256 is
`7d8a1bf5f0228c2012c7dc52fa05a4d9f02645bc8979119282bf638689be5daa`.
The clean CPU-only capture recorded 92.511 sampled CPU seconds. It detected
45.870-second opening, 14.050-second editing and 30.830-second split-transition
main-loop stalls, plus shorter stalls. Operation labels bracket actions;
they do not isolate exact method duration or establish scheduler causality.

The top full-stack self cost is **31.022 seconds in
`-[GSLayoutManager _sanityChecks]`** (33.5% of sampled CPU), followed by
Objective-C dispatch (18.709 seconds) and a partially symbolized GUI frame
(13.659 seconds). In the application-only tree, `setViewerMode:persistPreference:`
has 31.190 seconds inclusive; `layoutDocumentViews` has 25.050 seconds,
including 15.830 seconds under `OMDWin11SplitView adjustSubviews`. Those
inclusive frames overlap and must not be added together. The next investigation
should examine full-document layout work and repeated relayout during mode/size
changes, with deeper library symbols; this evidence does not prove a parser bug
or a retention leak.

Sombre Read/open and scrolling were captured separately while diagnosing
a failed mode-button action. The accepted Sombre edit capture starts in the
app's supported Edit mode, scrolls the source, inserts one `Q` through the
explicit private window and verifies Save by reading the changed file.
Saved SHA-256:
`25b3aa23b4259b76b794fd7720df2d42d9e2136c1818eede86cd43959cd3400a`.
It finishes cleanly with 5.852 sampled CPU seconds, a 4.600-second startup
stall and two roughly 350 ms stalls; 4.018 seconds of self samples are in
`GSLayoutManager _sanityChecks`. **The two themes did different actions and
these CPU totals are not a theme performance comparison.** The accepted Sombre
capture does not qualify the Read-to-Edit or Split transition.

Both accepted captures have no recording-quality warnings. Adwaita Split
and Sombre edited screenshots were inspected. Failed focus, shortcut, mode
transition and sandbox-socket attempts remain alongside the accepted evidence;
they are not reported as successful product workflows. Explicit owned-window
key delivery resolved the Sombre keyboard automation issue. No target app
source was changed. Evidence: `out/markdown-dogfood/{Adwaita,Sombre}/`,
including event timestamps, commands, traces, JSON, saved files and screenshots.

## LinDirStat: synthetic scan and startup cost

Unchanged source: `b9cf7b71bb4eca8595b5ffdb84ff8afbc7fc87d6`.
Native executable SHA-256:
`7ab32917ab62acf57af6eef98d1a4eb785584c6f60757637042decb44a10a121`.
The project built through its GNUstep CLI workflow. The dataset has 40,960
regular files in 256 subfolders: 188,743,680 logical bytes (180 MiB), five
extensions, no links and no user data. The deterministic ordered content/path
manifest SHA-256 is
`827393fc2678701959f86f95191f02794af80791285278b662cbd365e881698b`.

The private Adwaita GUI completed scanning and displayed exactly 40,960 files,
256 folders and 240 MB physical space. The larger physical total reflects
filesystem allocation for the generated 1–8 KiB files; it is not the logical
byte total. The directory tree, extension list and treemap rendered and
selection actions were exercised. The completed screenshot was inspected.
The app's displayed scan duration was 0.1 seconds. The harness observed the
finished window at 3.795 seconds including startup and a deliberate two-second
settling delay, so that number is not a scan-duration benchmark.

The clean capture has 1.465 sampled CPU seconds, one 519.9 ms main-loop stall
starting roughly 0.912 seconds after recording, and 148,908 KiB loaded/peak RSS.
The application-only tree attributes 298 ms inclusive to `setUpMainWindow`
(20.3% of CPU); startup/UI preparation is an observable cost in this small warm
scan. The trace alone does not establish the cause of the stall or behavior
for millions of files, inaccessible directories, hard links or large real disks.
The first two harness attempts failed readiness polling and were retained;
only the final completed capture is qualified. No delete/cleanup action ran.
Evidence: `out/lindirstat-dogfood-final/`, generated inputs and `dataset.json`
in `out/lindirstat-dogfood/`.

## Arlen prototype

The [prepared response-header packet](upstream-review/arlen-header-serialization.md)
records isolated prototype `64c2ec6ab4d32b9cac3acfef969615955ef46c9e`,
26 passing response cases plus one header-contract case, and the matched
900-request CPU-only pair. Total CPU increased from 830 to 917 ms while
serializer inclusive cost was nearly unchanged (117 to 115 ms). This does
not establish an overall optimization. The packet and patch remain local.

No additional Performance Dashboard usability defect was confirmed by these
application runs. The conditional stretch fix is therefore omitted; the
verified memory changes and checks are in [the validation record](v0.1.4-validation.md).
