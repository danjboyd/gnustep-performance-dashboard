# Local CLI symbol-coverage change

The primary CLI metric counts unresolved display-frame entries across distinct
stacks referenced by the process's recorded events, broken down by module.
This includes Allocations-only traces. It is neither a unique-PC count nor a
sample-frequency count; repeated frames in distinct stacks count again. The
lead selected this denominator after the initial design review. For CPU traces,
a separate weighted line uses CPU sample overrun weights and excludes wall
samples. No CPU line is printed when there are no CPU display frames.

`gstrace info` shows the process-wide summary. Reports show it only when
`--symbol-summary` is requested, and label its whole-process scope even if the
report has range/thread filters. CSV and default report output remain separate.
Modules with unresolved frames are listed, with full paths when basenames would
collide. Output observes naming coverage; it does not assert that an entire
module has no symbols or diagnose an unwind failure.

The symbolicator now recognizes reserved legacy fallback labels from embedded
name snapshots against their exact raw address or image-name/hex-offset form.
Ordinary function names containing `+0x` are not treated as fallback labels.
Zero non-leaf addresses are kept at zero rather than wrapping to UINT64_MAX.
These two existing edge cases were reproduced before the change in a small
isolated harness; embedded/reopened unknown status and zero-PC behavior are
now regression assertions. No sidecar format or trace-format version changed.

## Checks run

- Fresh framework/CLI build, then all **30** framework unit tests passed. The
  new tests cover mixed naming within an image, referenced/unused stacks,
  repeated samples, zero return PCs, legacy embedded names, module counts,
  allocations-only input, agent filtering and CPU weights excluding wall data.
- **All 49 checks passed** in `SKIP_GUI=1 make check`, exit 0, including real C
  and Objective-C recorder paths and the existing known-JPEG classification
  unit. AppKit/GUI gates were skipped explicitly. The two conditional live
  JPEG label/hide checks did not execute because that probe detected zero
  leaks on this SDK; no complete release-candidate gate is claimed.
- **All three CLI scenarios passed** on x86_64: Allocations-only, CPU-weighted
  and empty/unreferenced-stack traces. They check summary/module counts,
  opt-in report behavior, embedding/reopening and CSV output.
- The same three CLI scenarios passed after a native aarch64 framework/CLI
  build in the owned Debian 13 QEMU/TCG VM. No real application hardware trial
  was rerun, and no production host was accessed. The VM used a separate copy
  of the already qualified port source with only this framework/CLI/test overlay.
  This is headless CLI coverage, not an arm64 AppKit or release-package gate.

A first unit invocation lacked the fresh worktree's helper binary; building
that prerequisite made the complete suite pass. A first CLI harness expected
an XML plist from GNUstep's embedding writer; the harness was corrected for
its existing legacy text format. Those failed setup/harness logs are retained.
The owned VM had stopped since the earlier interval; its idle disk was checked
before booting it, and its loopback-only SSH connection was restored. No key,
secret, remote ref, update feed or installed runtime was changed.
