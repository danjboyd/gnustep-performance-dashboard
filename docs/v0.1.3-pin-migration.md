# v0.1.3 input migration preparation

The `next/v0.1.3-pins` development branch starts from the frozen v0.1.2
source plus the client layout follow-up. It leaves the qualified v0.1.1 and
v0.1.2 refs and packages intact. The OpenTrace signpost target stays on its
separate draft branch until the target route is selected.

Linux now pins gnustep-cli-new v0.1.2, using the published bootstrap and
signed release manifest with exact archive hashes. The CLI archive changes;
the toolchain archive is byte-identical to the previously pinned payload.
Its patched `GNUstep.sh` supplies the runtime library path, so the duplicate
exports in the package build/stage scripts are removed. Staging sources the
same activation script rather than depending on its caller's environment.
The source-navigation fixture explicitly enables debug information because
the managed toolchain's default Objective-C flags do not include `-g`.

The packager pin moves to published v0.1.4 at
`211d9136ca2359fdb91af8245b5c86b497e07220`. The vendored updater is synced from
that same exact revision, including corrected install-failure alert
punctuation. Its three documented `HAVE_MODE_T` compatibility lines remain
for the currently pinned Windows input. The vendoring record identifies this
source and local difference separately from the packager executable pin.

Windows still uses the verified v0.1.1 inputs while waiting for a published
CLI v0.1.3 with perl and signature verification in its PowerShell bootstrap.
The archive filename is now selected from the input lock instead of embedding
the old version in the extraction command. After publication, update all
bootstrap/metadata/archive hashes and corresponding-source inputs together,
then run native Windows validation. Remove `HAVE_MODE_T` only when the chosen
toolchain's libdispatch headers no longer need it; the unrelated rolling
MSYS2 CI environment needs its own check before removing its workaround.

`fetch-toolchain.py` continues authenticating signed metadata because Windows
packaging extracts the ZIP directly and does not invoke the bootstrap. A
bootstrap signature check cannot protect that separate path. Release assets
must remain immutable; migrated inputs produce new review packages and never
replace an existing candidate's files.
