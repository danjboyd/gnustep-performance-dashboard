## Recording through exec wrappers

The unchanged RC1 reproducer `/bin/sh -c 'exec "$1"' wrapper /path/to/cburn`
produced a zero-duration, zero-sample, unclean stream labelled `/usr/bin/dash`.
The agent scrubbed its own LD_PRELOAD and GSP_OUTPUT before the shell's exec,
so the replacement executable never loaded the agent.

The agent now preserves injection settings across exec, with target-PID and
recorder-parent guards retaining default child exclusion. Each exec publishes
a complete replacement header via atomic rename; a live reader never maps
an inode while it is truncated. Reload recognizes the changed stream epoch
and replaces the prior process definitions, samples and analyses. This keeps
the **final same-PID image**, rather than preserving pre-exec history. Dynamic
preload restrictions still apply, and forked children need explicit following.

Minimal and delayed C wrapper checks finish cleanly with attributed CPU
samples. The regression suite also checks that a fork/exec child remains
excluded; it does not assert clean finalization of a shell that bypasses
normal exit handlers without exec. The synthetic reader test replaces a
stream atomically and verifies new definitions/sample weights, then a no-op
reload. Real ScreenshotTool launched through our shell wrapper finishes
cleanly under private Adwaita and Sombre displays (921 and 732 CPU samples in
the retained six-second checks). Both screenshots were inspected. The agent
continues to link only libc and the system loader.

## Responsive loading and memory

Existing trace opens show an indeterminate standard progress bar immediately.
A worker owns the unpublished trace, parses/resolves records, prepares initial
analyses, loads embedded symbol dictionaries and builds the initial CPU call
tree. Only the finished model transfers to the main thread. AppKit construction,
publication and drawing stay on the main thread. Closing during a load discards
the eventual result without an alert; it does not interrupt the parser.

Known allocation-stack definitions resolve immediately, avoiding a pending
reference for every allocation. Empty pending storage is freed before sorting.
A unit test covers stack definitions both before and after their allocation.
A baseline/fixed CLI export of the large trace has identical JSON after sorting
Top Functions only to ignore equal-weight tie ordering. The final package's
framework binary matches the one used for that equivalence check.

The retained 340,831,476-byte ScreenshotTool trace was opened three times on
private Xvfb using the benchmark branch at
`865862f9ed8fd6da89b8dacbdedcb1a36bf1e63a`. Before uses exact v0.1.3 RC1;
after uses the local development package below. Both use the **same RC1
recorder**, identical input hashes, and warm caches from hashing the input.
All six recordings finished cleanly with zero dropped samples. Input and
package hashes were unchanged at the end of each run set.

### Same-input memory comparison

The unchanged 340,831,476-byte real trace and frozen ea576ea recorder were used
for both builds. The allocation self-profile identified large event-sort scratch
arrays and over-reserved analysis storage. Commit
`80bbeccf4922f75e45831c96a73313017336d743` sorts stable event indices and then
permutes records in place, trims the final event storage and reserves analysis
records from allocation count rather than allocation-plus-free count. The final
`ebc6d64` representation keeps compact derived fields referring to finished
process event storage. A caller requesting the public contiguous records array
materializes it lazily; that operation can increase memory again. Live streams
keep their independent expanded records. Finished epochs remain sealed until
a replacement exec header is detected. Worker autoreleased temporary objects
are drained before the finished model is published. No allocator trimming API
is used.
