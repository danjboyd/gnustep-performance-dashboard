# ScreenshotTool dogfooding with v0.1.3

Local investigation, October 29, 2026. Findings are for the Performance
Dashboard project lead. No ScreenshotTool submission or release is approved.

## Reproduction and identities

Recorder/application source: `ea576eaebb0ac992ca8cd9f9cfe00878b70fe6db`.
ScreenshotTool source: `4b65100875716c32b0c1b314fc7326874eb7ab68`;
its libs-sharing input is `cbc6726c554e27fcb372d01f6eb5691de75da08e`.
The target was built with the local GNUstep environment and `debug=yes`,
inside our separate clone, without changing another agent's checkout.

A new private Xvfb display shows ScreenshotTool's checked-in synthetic
security-settings sample as wallpaper. ImageMagick captures that display to
a fixed 1920 x 1080 PNG. ScreenshotTool opens the captured PNG; physical
mouse/key input adds a highlight and arrow and saves `workflow-export.png`.
This exercises the external X11 capture/open route, **not** the Linux
Screenshot portal: the private display has no desktop portal. The wallpaper
contains synthetic account data, not a capture of Dan's desktop.

Each theme gets a separate private passwd home, defaults, runtime and
Xvfb display. The recorder runs CPU, allocations and leaks (10-second leak
interval, 65-second recording). Both exports were visually inspected;
the input and output pixels differ where the annotations were added.
A separate 35-second CPU-only run under Adwaita uses the same image/input
sequence to distinguish application CPU from combined-instrument overhead.
All accepted recordings finished cleanly with zero dropped samples.

Evidence is retained under ignored `out/linux-development-20261029/dogfood/`:
`automated.py`, per-run `events.json`, screenshots, exports, `workflow.gstrace`,
`info.txt`, `application-calltree.txt`, and `identities.json`. Embedded symbols
are retained before changing the target executable. The earlier interactive
save-dialog attempt is diagnostic only: it did not finish cleanly and is not
an accepted workflow run.

## Measurements and proposed ScreenshotTool fix

| Recording | Sampled CPU | Hidden thumbnail callback weight |
|---|---:|---:|
| Adwaita, CPU + allocations + leaks | 7.344 s | 327 ms |
| Sombre, CPU + allocations + leaks | 4.947 s | 314 ms |
| Adwaita, CPU only | 2.731 s | 289 ms (10.6%) |

These are individual runs with different themes/instrument overhead, not a
cross-theme speed comparison or production benchmark. The callback is
`-[AppDelegate loadEmptyStateThumbnailForCard:path:key:]`'s load block.
The CLI tree with system libraries hidden charges descendant library costs
to the nearest application frame; these weights are not direct self time
in the source statements.

The CPU-only trace shows `openImageAtURL:` -> `addRecentDocumentURL:` ->
`rebuildOpenRecentMenu` -> `refreshEmptyStateRecents` taking 52 ms, followed
by 289 ms attributed to the delayed thumbnail load. Source inspection shows
that `refreshEmptyStateRecents` constructs cards even with an image open;
the delayed load only checks `weakCard.window`, which remains non-nil for
cards in the hidden empty-state view. Saving the annotated image repeats
recent-file work. None of these thumbnails is visible in this workflow.

Proposed local fix: defer recent-card refresh while the canvas has an image,
mark the cards stale for the next empty state, and skip a queued thumbnail
load when its card or an ancestor has become hidden. Keep the normal
empty-state refresh when the last image closes. A focused regression should
fail before the change and check both hidden-state suppression and the
return to visible recent cards. This is a small candidate for the
ScreenshotTool owner to review after the exact-hash upstream sign-off.

The largest application-attributed save-panel frame was 1.33 s in the
combined Adwaita run and 664 ms in the CPU-only run. It includes native modal
panel/library work; PNG encoding itself was 72/84 ms respectively. It does
not establish an application busy-loop defect or justify changing encoding.

The Adwaita conservative scan found 5,246 blocks (340.40 KiB), of which
5,229 are labelled known GNUstep leaks. The remaining 17 total 910 bytes;
the retained tree points largely to fontconfig initialization. This is not
proof of a new ScreenshotTool retention bug. Persistent allocations at stop
are also not leaks merely because the app remains open.

## Dashboard observations and follow-ups

The combined Adwaita trace opened in the candidate Dashboard with CPU,
allocation and leak tracks visible and matching the CLI counts. Launch to
the visible trace window took 3.55 s; the viewer process high-water RSS was
1,012,120 KiB, with 610,556 KiB resident at the screenshot. This includes
application startup and is not an isolated OpenTrace timing measurement.

- **v0.1.3:** preserve this real recording and its source identities alongside
  the candidate gate results. No new analysis-correctness defect was
  demonstrated by the capture/annotation/export workflow.
- **v0.1.4 investigation:** profile memory and responsiveness while opening
  multi-million-allocation recordings; consider visible progress/cancellation
  if parsing/symbolication blocks the UI. Reproduce before choosing a fix.
- **v0.1.4 investigation:** improve explanation of combined-instrument CPU
  overhead and the costs charged to application frames when system libraries
  are hidden. The CPU-only comparison materially changed the interpretation
  of this workload; do not market the combined totals as app-only CPU.

## Local prototype result

The isolated ScreenshotTool prototype is commit
`aa5b52abbbee5af693b9c14e73ec32bfef5b336b`. It changes only
`Source/AppDelegate.m` and `Tests/LaunchCostProbe_test.m`. It is not approved
for submission and was not sent to the ScreenshotTool owner.

The focused hidden-recents test failed on the original implementation
(one failure among seven launch-cost tests: one hidden-thumbnail request
instead of zero). With the change, all seven launch-cost tests and all four
empty-state tests passed under **both Adwaita and Sombre**. The tests check
that an open image does not request a hidden thumbnail and that thumbnails
resume after the last image closes. An initial test compile error was
corrected before the recorded before/after assertions; it is not counted as
the demonstrating failure.

The CPU-only baseline and prototype use identical 1920 x 1080 captured
input bytes, physical input sequence, instrumentation and private defaults.
The exported annotated PNGs are also byte-identical:
`fb08caf27abf94f7e4131809e98498cae64e86af1c2e696c945097f33ad0fb7f`.
Both traces finish cleanly with zero drops.

| CPU-only measurement | Original | Prototype |
|---|---:|---:|
| Total sampled CPU | 2.731 s | 2.508 s |
| Delayed hidden-thumbnail callback | 289 ms | no sampled callback |
| `openImageAtURL:` inclusive weight | 85 ms | 51 ms |
| Refreshing recents under the image-open path | 52 ms | no sampled refresh |

The 223 ms lower total (8.2%) is a **single-pair observation**, not a
statistically established general speedup. Other frame costs vary, and
both drivers intentionally wait for input; elapsed recording duration is
not operation latency. The stronger result is the regression test and the
removal of sampled work for invisible thumbnails while preserving exact
export bytes. More repetitions and other image/project sizes are needed
before a performance claim or upstream submission.

Comparison receipts and traces are `dogfood/cpu-comparison.json`,
`Adwaita-cpu-baseline/` and `Adwaita-cpu-prototype/` under the retained output
root. The prototype's `provenance.json` records its actual source and binary
hash; the original shared driver has a baseline-source literal in its
`result.json`, so that literal must not be used as the prototype identity.
No Dashboard implementation change was needed for this investigation.
