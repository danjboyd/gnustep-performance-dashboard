## Cross-platform trace contract

`Tests/trace-portability.py --gstrace PATH --synthetic` independently writes
little-endian format-v1 traces with Linux and Windows executable paths. It
checks addresses above 4 GiB, Unicode, weighted/out-of-order samples, late
stack/string definitions, unknown records, partial final records, diagnostics,
embedded symbols and exports.

Native fixture recordings are exchanged through CI artifacts. `--capture`
copies a fixture trace, embeds symbols and stores its JSON baseline and file
hashes. `--verify` reads that bundle on the other OS, compares the complete
summary (allowing floating-point roundoff and ordering ties), and checks JSON,
speedscope, collapsed-stack export and self-comparison. No target binaries or
user recordings are exchanged. Synthetic tests supplement native tests; they
do not prove Windows injection or GUI operation.

```sh
python3 Tests/trace-portability.py --gstrace Tools/gstrace/obj/gstrace --synthetic
python3 Tests/trace-portability.py --gstrace Tools/gstrace/obj/gstrace \
  --capture Tests/out/cburn.gstrace --output Tests/out/native-linux
python3 Tests/trace-portability.py --gstrace Tools/gstrace/obj/gstrace \
  --verify Tests/out/native-linux
```

The capture output must be a new directory. Keep CI evidence for both directions:
Linux recording → Windows reader and Windows recording → Linux reader.

## Windows acceptance gates

1. Install, launch and uninstall MSI on a supported Windows client host without
   a developer GNUstep installation. Verify per-user ownership and one installed
   product entry after upgrades. Also test the portable ZIP from spaces and
   non-ASCII paths.
2. Record two real GNUstep GUI workloads with CPU, allocations/leaks, hangs and
   signposts. Retain executable identities, input description, screenshots and
   clean-stop evidence; record unverified instruments explicitly.
3. Exercise launch, attach, stop, target exit and crash. Verify the current
   once-per-process attach restriction is visible rather than a silent failure.
4. Save/reopen, embed symbols, export and compare repeated workloads. Check
   optimized stacks, stripped/missing targets and source-line prerequisites.
5. Test RC→RC→final MSI updates, refused downloads/digests and installer failure.
   Windows Installer compares the first three numeric version fields; the
   packager allows same-version upgrades. The in-app feed's semantic version
   check provides finer RC ordering. Keep RC feeds separate from stable feeds.
6. Preserve the Linux regression suite and both theme checks. Publish only the
   assets whose exact hashes and source revisions have acceptance evidence.

## Packaging inputs and open decisions

Debian retains the v0.1.0 toolchain pins. The toolchain agent reports Windows
MSYS2 CLANG64 payloads in stable gnustep-cli-new v0.1.1; verify and digest-lock
those inputs before execution. Its PowerShell bootstrap checks payload hashes
but does not itself verify the manifest signature, so acquisition must verify
both the pinned metadata hashes and signature before invoking it.

The pinned packager v0.1.1 emits an MSI plus a portable ZIP from the transformed
install tree. Its update feed advertises the MSI; ZIP users update manually.
Keep provenance, metadata, dependency notices and corresponding sources with
both binary formats. Hosted-runner smoke is not clean-client acceptance.

Ubuntu 24.04 inputs are unpublished and deferred. Signing and final release
publication remain decisions for review. Do not change system installer policy
or request certificate credentials merely to make an acceptance test pass.

## Release assembly contract

`scripts/assemble-release.py` consumes flat artifact directories, validates
feed URLs, channels, payload hashes/sizes and clean provenance for one full
source commit, then writes a new output directory with checksums and feeds.
It never modifies existing output or publishes anything. Corresponding-source
archives must contain `sources/PerformanceDashboard.tar` (any outer directory
name is allowed), generated by `git archive`; its embedded commit must match.

The Linux producer supplies the AppImage, zsync, feed, provenance and
`PerformanceDashboard-VERSION-sources.tar.gz`. The Windows producer supplies
MSI, portable ZIP, feed, provenance and
`PerformanceDashboard-VERSION-windows-sources.tar.gz`. The Windows provenance
must include the portable ZIP under `relatedArtifacts`. Missing sources or a
stale/unreferenced binary prevent assembly. Dependency-source completeness and
native installation remain independent acceptance gates.

The manual **Assemble Linux and Windows candidate** workflow downloads both
producer artifacts from this repository. Dispatch it on the exact commit they
both built, with their run IDs. It produces only a `combined-candidate` review
artifact; it has no permissions or steps to tag, publish, or deploy feeds.

The Windows toolchain lock uses stable v0.1.1. Both its metadata hashes and
signature were independently verified on Linux on October 19. The public key
in `packaging/toolchain-release-public.pem` is the production key from the
already digest-pinned v0.1.0 POSIX bootstrap; it is not taken from newly fetched
metadata. `fetch-toolchain.py --platform windows --metadata-only CACHE` verifies
without installing anything. Omit `--metadata-only` to verify all payloads
before running a bootstrap. The cache is rechecked on every invocation.

## Windows corresponding-source preparation

`scripts/windows-source-inventory.py` maps binary owners from the pinned
toolchain's `input-manifest.json` through its hash-verified `msys2-sync`
databases. It uses the explicit MSYS2 source-package base, including split
packages, and checks binary versions and hashes against the snapshot. It
does not execute package recipes or claim that candidate URLs are verified.
Use repeated `--package NAME` arguments for the owners of the actual staged
files; omitting them inventories the entire development toolchain.

The published Windows input revision
`d66adffe5311bc1e60e01f088e2502ceede70277` maps 163 binary packages to 143
source packages. `packaging/windows-core-sources.json` pins the six downloaded
GNUstep/runtime source packages. Their archives contain the upstream source
tarballs, PKGBUILD, .SRCINFO and recipe patches. This is a partial source
inventory, not the complete corresponding-source archive. The final package
still needs ownership mapping for every bundled runtime file, dependency
license texts, the toolchain assembly recipes/header adjustments, the exact
theme source, and the application archive for its build commit.

## Integration test findings

The first trace-exchange CI run passed Linux but stopped in the existing
Windows attach-signpost test: its two-second recording contained CPU samples
but no signpost calls. Long fixture intervals could span the whole recording.
The fixture now optionally emits frequent `AttachHeartbeat` events during the
same workload, and the attach check requires those events. The launch check
continues to require four complete `Round` intervals. A local Linux recording
verified four intervals and 40 heartbeat events; native Windows CI remains
the authority for the attach behavior.

Run [39335022313](https://github.com/danjboyd/gnustep-performance-dashboard/actions/runs/39335022313)
passed the Windows recording checks and all six synthetic portability cases,
then exposed a native Linux→Windows mismatch. Embedded symbol tables omitted
unnamed function labels, so reopening on another host changed their offsets
or resolved them against a different local library. Commit `5b91679` preserves
all frame labels in the existing address-to-string sidecar format and handles
zero return addresses without unsigned underflow. The framework's 19 unit
tests and six synthetic cases pass locally. The published v0.1.0 reader also
reads a newly embedded native fixture with matching summary and exports.

The artifact-only Linux release build
[39335416241](https://github.com/danjboyd/gnustep-performance-dashboard/actions/runs/39335416241)
passed for `0ba4151`, version `0.1.0-integration.1`, including strict assembly.
All downloaded artifact checksums matched. This validates the packaging path;
it is not a v0.1.1 release candidate and predates the symbol snapshot fix.
