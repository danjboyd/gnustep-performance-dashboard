# Path to v0.1.0

v0.1.0 is a Debian 13 amd64 release. The deliverable is an AppImage,
its zsync file, checksums, provenance and update feed. Windows stays in
development CI but is neither a release dependency nor a shipped asset.
Building Dashboard requires Clang/libobjc2; profiling GCC C targets is
supported independently. CPU profiling of Debian 13 GCC/legacy-runtime targets is separately tested;
class labels and Zombies with that runtime remain unverified.

The release promise: launch a GNUstep application, find CPU work and main-thread
stalls, attribute allocations and leak candidates, save/share the recording,
and compare a repeated workload with gstrace. No new instruments are required.

## Gate 1: trustworthy recordings and saved data

- Save As to the same path or a symlink alias preserves the recording.
  Replacing another recording stages the copy first; failed copying preserves
  both originals. Replacement failures restore the old destination or report
  the location of its retained backup.
- Denied process-memory reads yield an unavailable leak scan, never a result
  claiming that all blocks leaked or none leaked. CLI reports/comparisons fail
  for an unavailable latest scan; JSON identifies the unavailable result.
- Dropped samples, unfinished recordings, unavailable scans and frame-pointer
  fallback appear in recording warnings. Missing END is only a warning after
  recording stops, not while recording is in progress.
- Unit and end-to-end regressions cover the above.

## Gate 2: reproducible Linux validation

Source GNUstep.sh, install tools-xctest, Xvfb, xdotool, ImageMagick,
Adwaita, Sombre, GCC, Clang, GNU time and libunwind, then run:

```sh
scripts/check-linux-release.sh
```

The gate requires the full suite, including GUI checks with no skips, and
GCC/Clang C agents and targets at -O0/-O2 without frame pointers. It also
checks embedded names after the target executable is moved away and runs a
60-second allocation soak requiring at least 100,000 events and multiple scans. Review
`Tests/out/gui-Adwaita.png` and `Tests/out/gui-Sombre.png` visually.
Logs and source identity are kept in `Tests/out/release/`; a working-tree
patch and list of untracked files disclose a non-release tree.

The automated compiler matrix does not establish GCC Objective-C/legacy
runtime compatibility. Add an isolated distro GNUstep toolchain job before
expanding that support claim; do not mix runtimes in one process.

## Gate 3: package and useful workloads

Build a local package with `scripts/package-linux.sh --version 0.1.0-rc1`.
A dry-run package is development evidence only. Preserve the package hash,
provenance, logs and results for every candidate.

Before approving an RC, complete and record these acceptance checks:

| Check | Required evidence |
|---|---|
| AppImage on a clean supported Linux install | Launch, record from app and bundled CLI; no development-tree libraries; optimized stack names and source lines |
| Two real GNUstep GUI apps | App revision, repeatable interaction, CPU/allocations/leaks recordings, actionable stack, save/reopen and symbol embedding |
| Sustained allocation recording | At least 60 seconds, eight worker threads, periodic scans, clean stop, trace size, peak recorder/target RSS and viewer response |
| Interactive diagnostics | Unavailable scan and unfinished trace visibly warn in Adwaita and Sombre |
| Helper | Install, same-user attach, stop, uninstall on disposable machine; exercise denial cases without weakening policy |
| Update | Local test feed: RC1 offers RC2, restart installs RC2, relaunch and recording work; failed download leaves RC1 usable |
| Distribution compatibility | Test Debian 13 and Ubuntu 24.04, or narrow the download page to the systems that actually pass |

The AppImage bundles GNUstep, but the target needs host libunwind for DWARF
unwinding. Source lines currently use host `/usr/bin/addr2line`. Explicitly
document these requirements; test missing libunwind as a degraded capability.
Do not infer clean-machine support from a developer-machine launch.

## Gate 4: candidate and publication

1. Review the final diff, test evidence, known limitations and package inputs.
2. Commit the reviewed implementation; rebuild from the clean commit with
   pinned inputs (`scripts/package-linux.sh --release --version 0.1.0-rc1`).
3. Dan approves the exact RC tag and publication separately. Publish the
   candidate assets before its update feed; test the published candidate.
4. Fix candidate defects, repeat affected gates, and make another candidate
   if code or package inputs change.
5. Dan approves v0.1.0 tagging/publication after all gates pass. Publish final
   assets, then stable feed. Archive the evidence and release notes.

No script tags, publishes, or sends upstream contributions. The release
workflow assembles Linux artifacts only. Pending checks stay pending;
feature completion alone does not close the release.

## Evidence ledger

See [v0.1.0 validation](v0.1.0-validation.md) for dated results and outstanding
acceptance work. This ledger is the handoff between implementation and release
approval, not a declaration that v0.1.0 has shipped.

The repeatable startup/image-load and directory-scan smoke workloads can be
run against existing binaries after sourcing GNUstep.sh:

```sh
Tests/real-app-checks.sh /path/to/ScreenshotTool.app/ScreenshotTool /path/to/LinDirStat.app/LinDirStat
```

This uses isolated preferences, a private display, a repository screenshot and
1,200 generated files. Inspect `Tests/out/real-apps` screenshots and stacks.
It covers CPU/Leaks recording and embedded names for both apps, not a manual
before/after optimization exercise or the package's clean-machine contract.
