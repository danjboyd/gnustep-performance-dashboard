## Dashboard investigations

1. Large-trace responsiveness and memory. The unchanged RC1's three warm-cache
   instrumented opens of a 340,831,476-byte trace showed 1.763–1.801 s OpenTrace
   intervals, 2.720–2.780 s main-loop hangs, 550,556–551,856 KiB loaded RSS and
   986,840–988,448 KiB peak RSS. Separate parsing, resolution, allocation analysis
   and view-model construction before choosing a fix. Investigate background
   loading with progress/cancellation and bounded representations; preserve
   main-thread-only UI changes, source navigation and analysis results. Repeat
   the same benchmark with identical input/binary receipts and add larger and
   smaller traces. The existing benchmark is diagnostic, not release acceptance.
2. Launch through exec wrappers. A package GUI recording launched ScreenshotTool
   through a shell wrapper: the app opened but its trace was empty and unclean.
   The native executable route passed. Reproduce with a minimal C exec fixture,
   inspect agent/trace ownership across exec, then add an end-to-end regression
   before a product fix. Do not claim native success covers scripts/wrappers.
3. Recording overhead explanation. Combined CPU/allocation/leak recording changes
   the target's work and memory. Explain instrument costs and use a separate
   CPU-only repeat when interpreting hot paths. Add user-facing information only
   where it helps select recording types; do not present sample weights as
   elapsed latency or a one-pair result as a general speedup.
